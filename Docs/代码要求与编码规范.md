# 飞控工程代码要求与编码规范

## 1. 文档目的

本文档汇总当前 STM32H743 飞控工程已经确认的代码要求、排版规范、架构约束和验证标准。

规范的核心目标是：

1. 让代码更容易阅读、理解、调试和维护。
2. 保持模块职责清晰，避免同一功能在多个文件中重复实现。
3. 保持中断、DMA、FreeRTOS 和缓存相关代码安全可靠。
4. 格式整理原则上不改变原有业务逻辑；功能修改必须有明确目的并完成回归测试。
5. 不以机械限制代码行数为目标，以单一职责、复杂度和可测试性作为主要判断依据。

参考代码风格：

```text
D:\myFiles\RM\RMcontrol\basic_framework_mc02-master
```

当前整理后的工程：

```text
D:\myFiles\RM\uav_basic_framework\new\my_new_uav_basic_framework_readable
```

---

## 2. 工程修改原则

### 2.1 使用独立工程副本

- 大规模整理、重构和功能移植必须在新建文件夹中完成。
- 不直接覆盖原始工程，确保原始版本可以随时对比和恢复。
- 不删除用户已有代码，不使用破坏性 Git 或文件系统操作覆盖用户修改。

### 2.2 区分排版修改和功能修改

排版修改包括：

- 合并不必要的垂直换行。
- 统一缩进、空格、括号和对齐方式。
- 调整函数、变量和代码段的排列顺序。
- 补充中文注释。
- 将公共类型和数据结构移动到头文件。

功能修改包括：

- 改变算法、初始化顺序、协议解析或传感器配置。
- 修改中断、DMA、任务优先级。
- 修改缓存、MPU、链接脚本和内存区域。
- 新增设备驱动、任务、消息或融合逻辑。

排版修改不得暗中改变功能；功能修改必须通过编译、回归测试和实机验证。

## 3. 目录和分层职责

工程保持以下分层：

```text
Core/           STM32CubeMX 生成代码、HAL 初始化、中断入口
Bsp/            UART、SPI、I2C、PWM、时间戳、环形缓冲区等板级封装
Modules/        BMI088、BMI270、SPL06、TFmini、MTF02、SD 卡等组件
Application/    任务、数据路由、姿态解算、控制和系统初始化
Middlewares/    FreeRTOS、FatFs、USB、SEGGER 等第三方中间件
Tests/          协议、数学和代码质量回归测试
Docs/           工程说明、性能报告和编码规范
```

依赖方向应保持为：

```text
Application
    ↓
Modules
    ↓
Bsp
    ↓
HAL / Core
```

禁止出现以下情况：

- BSP 反向依赖 Application。
- 通用数学库依赖具体传感器模块。
- 一个传感器模块直接操作另一个传感器的私有状态。
- Application 绕过已有 BSP 封装直接重复实现 UART、SPI 或 I2C 操作。

## 4. 文件和函数规模

采用软阈值，不使用“`.c` 文件最多 125 行、函数最多 25 行”之类的硬性门槛。

### 4.1 函数规模

- 普通函数目标不超过 50 个有效代码行。
- 超过 80 个有效代码行必须说明原因或进行评审。
- 一个函数只完成一个明确职责。
- 任务入口函数应主要体现流程，不应塞入大量底层计算和协议细节。

推荐形式：

```c
static void SensorHub_Task(void *argument)
{
    SensorHub_WaitForEvent();
    SensorHub_ProcessSensors();
    SensorHub_PublishData();
}
```

允许较长的函数：

- STM32 外设初始化函数。
- 寄存器配置序列。
- 协议状态机。
- 数学推导过程。
- ESKF 矩阵运算。

这些例外必须有清晰分段和相应测试。

### 4.2 圈复杂度

- 圈复杂度超过 15 时重点检查。
- 圈复杂度超过 20 时原则上重构。
- 优先拆分职责和状态处理，不为了降低数字而制造无意义的小函数。

### 4.3 文件规模

- `.c` 文件通常 300～800 行可以接受。
- 文件是否需要拆分，以模块单一职责为判断标准。
- 不为了满足行数限制把一个完整驱动拆成大量难以跳转的小文件。
- 一个文件不得混合多个无关设备、协议或算法。

---

## 5. 头文件规范

### 5.1 数据结构放置

以下内容统一放在 `.h` 文件：

- 公共结构体。
- 模块实例类型。
- 枚举类型。
- 对外可见的状态类型。
- 公共宏和配置项。
- 对外函数声明。
- 需要被调试器观察的数据类型。

不要在 `.c` 文件中定义上层需要了解或复用的结构体。

### 5.2 头文件内容顺序

建议顺序：

```text
文件说明
头文件保护宏
C/C++ 兼容声明
依赖头文件
公共宏和配置
枚举
结构体和类型
extern 数据声明
函数声明
结束保护宏
```

### 5.3 私有内容

仅限本文件使用的变量和函数必须使用 `static`。

真正只在单个 `.c` 文件内部使用、且不会被其他模块理解或访问的简单私有辅助类型可以例外；但本工程优先保证调试可见性和结构统一，复杂模块状态类型仍建议放在对应头文件。

---

## 6. `.c` 文件排版顺序

建议采用以下顺序：

```text
文件说明
#include
私有宏
私有静态变量
私有函数声明
初始化辅助函数
公开初始化函数
内部业务辅助函数
公开业务接口
任务入口或中断回调
调试和状态查询接口
```

初始化相关代码放在业务应用函数之前，使阅读者可以先理解模块如何建立，再阅读运行阶段逻辑。

代码段可以使用适量中文分隔标题：

```c
/* ========================== 初始化 ========================== */
/* ========================== 数据处理 ========================== */
/* ========================== 对外接口 ========================== */
```

分隔标题不能过密，避免每个小函数都增加视觉噪声。

## 7. 排版和格式

### 7.1 垂直换行

删除冗余的垂直换行。简单赋值、函数调用和条件表达式在行宽允许时保持单行。

不推荐：

```c
HAL_StatusTypeDef ret =
    SPITransRecv(
        spi,
        tx,
        rx,
        length);
```

推荐：

```c
HAL_StatusTypeDef ret = SPITransRecv(spi, tx, rx, length);
```

只有以下情况才合理换行：

- 单行超过格式化工具设定的列宽。
- 参数较多且每个参数都需要独立说明。
- 复杂布尔表达式需要分层展示。
- 矩阵公式或协议字段排列需要保持对应关系。

### 7.2 缩进和括号

- 使用 4 个空格缩进，不使用 Tab 混排。
- 使用 Allman 大括号风格。
- `if`、`for`、`while`、`switch` 后保留空格。
- 即使分支只有一行，也保留大括号。
- 指针星号与变量名保持项目统一格式。

### 7.3 对齐

相邻且语义相关的声明、结构体字段和初始化项可以适度对齐：

```c
uint32_t sample_count;
uint32_t error_count;
float    altitude_m;
```

不要为了对齐插入大量空格，也不要跨越很远的代码块保持人工对齐。最终格式以 `.clang-format` 为准。

## 8. 命名规范

### 8.1 模块接口

采用“模块名 + 动作”的形式：

```c
BMI088_Init();
BMI088_GetData();
SPL06_StartMeasurement();
SDCard_EnqueueFrame();
```

### 8.2 私有函数

私有函数同样保留模块前缀，便于搜索：

```c
static void BMI088_ParseGyro(const uint8_t *buffer);
```

### 8.3 单位后缀

物理量和时间变量必须在名称或注释中明确单位：

```c
uint32_t timeout_ms;
uint64_t timestamp_us;
float    altitude_m;
float    gyro_rps;
float    accel_mps2;
```

禁止使用无法判断单位的名称，如 `height`、`speed`、`time`。

### 8.4 状态和布尔值

- 布尔值使用能直接判断含义的名称，如 `initialized`、`data_ready`。
- 复杂状态使用枚举，不使用难以理解的魔法数字。
- 计数器名称以 `_count` 结尾，错误计数以 `_error_count` 结尾。

## 9. 中文注释要求

注释重点解释“为什么这样设计”，而不是逐字翻译代码。

必须说明：

- 函数的设计意图。
- 数据来源、目标和生命周期。
- 物理量单位及坐标系。
- 单位换算，例如厘米到米、毫 G 到 `m/s²`。
- FreeRTOS 临界区和多线程一致性原因。
- DMA 缓冲区、D-Cache 和 MPU 约束。
- 中断上下文是否允许调用 FreeRTOS API。
- 传感器寄存器配置的目的。
- 算法假设、异常条件和降级行为。

不推荐：

```c
count++; /* count 加一 */
```

推荐：

```c
/* 统计上一帧 DMA 尚未完成时到达的新 DRDY，用于判断总线是否跟不上输出速率。 */
stats->dma_busy_drop_count++;
```

复杂函数使用 Doxygen 风格说明输入、输出、单位和线程上下文。

## 10. 数学函数规范

- 通用向量、矩阵、四元数、限幅和数值检查函数统一放在：

```text
Modules/modules_Algorithm/user_math/user_math.c
Modules/modules_Algorithm/user_math/user_math.h
```

- 上层模块调用 `user_math`，不要在每个 `.c` 文件中重复实现 `Clamp`、向量模、欧拉角转四元数等基础函数。
- 只与单个算法内部推导强绑定、且没有复用意义的计算可以保留在算法模块中。
- 数学接口必须说明输入输出单位、坐标系、数值范围和异常值处理。
- 浮点计算必须检查非有限值、除零、小分母和矩阵非正定等情况。

## 11. BSP 和组件封装

### 11.1 BSP

BSP 只封装硬件总线和板级资源，不包含具体传感器业务。

`bsp_iic` 应参考 `bsp_uart` 和 `bsp_spi` 的风格：

- 统一注册配置。
- 实例化总线句柄。
- 支持阻塞和 DMA 操作。
- 统一事件回调。
- 明确总线忙、超时和错误状态。
- 不在上层模块重复调用底层 HAL 完成相同封装。

### 11.2 组件层

组件层负责：

- 芯片寄存器初始化。
- 数据采集状态机。
- 原始数据解析。
- 单位换算。
- 错误统计。
- 对上层发布一致的数据快照。

组件不得直接实现飞控业务决策。

### 11.3 SPL06

- 基于 `bsp_iic` 实现。
- 使用 DRDY 中断触发。
- 使用 I2C RX DMA 转运。
- 不使用没有必要的双缓冲区。
- 使用“DMA缓冲区复制到发布快照 + 序列锁”保证数据一致性。
- 保留 DMA 忙、启动失败、传输错误和解析错误统计。

## 12. 中断、DMA 和 FreeRTOS

### 12.1 基本规则

STM32 NVIC 中断优先级：

```text
数字越小，抢占优先级越高。
```

FreeRTOS 任务优先级：

```text
数字越大，任务优先级越高。
```

两套优先级方向相反，禁止混淆。

### 12.2 FreeRTOS 中断边界

当前配置：

```c
configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5
```

规则：

- NVIC 优先级 0～4 的中断不得调用任何 FreeRTOS API，包括 `...FromISR()`。
- NVIC 优先级 5～15 的中断可以调用 FreeRTOS 的 `...FromISR()` 接口。
- 中断中不得调用普通任务上下文 API。

### 12.3 当前关键优先级

```text
TIM2 时间戳溢出       0
BMI088 DRDY           1
BMI270 DRDY           2
SPI2/SPI3 DMA完成     5
USB OTG FS            7
SDMMC1                8
TIM17 HAL Tick       15
```

设计要求：

- BMI088/BMI270 DRDY 只记录时间戳、检查状态并启动 DMA。
- DRDY 中断不得直接通知任务。
- SPI DMA 完成中断保持优先级 5，在此调用 `vTaskNotifyGiveFromISR()`。
- USB 和 SD 卡不得抢占 IMU 关键链路。
- TIM17 HAL Tick 使用最低优先级，避免每 1 ms 干扰 IMU。
- TIM2 溢出约 71.58 分钟一次，保持优先级 0，保证 64 位时间戳跨回绕一致。

### 12.4 ISR设计

- ISR 尽量短。
- ISR 中不做浮点算法、协议解析、文件操作或长循环。
- 中断只做清标志、时间戳、状态切换、启动 DMA 和必要通知。
- 复杂处理放到高优先级任务。
- 所有高频 ISR 保留次数、最大耗时、错误和丢帧统计。

## 13. DMA、D-Cache、MPU 和链接脚本

STM32H7 开启 D-Cache 后，DMA 一致性必须显式处理。

### 13.1 DMA 缓冲区

DMA 缓冲区必须满足以下一种方案：

1. 放入 MPU 配置为不可缓存的 SRAM 区域。
2. 在 DMA 边界正确执行 D-Cache clean/invalidate。

禁止：

- 把 DMA 缓冲区放入 DTCM。
- 未做缓存维护就让 DMA 直接访问可缓存内存。
- 使用未对齐的缓存维护地址和长度。

### 13.2 内存放置

- 高频算法状态和高优先级任务栈可以放入 DTCM。
- ESKF、姿态解算等热点函数可以放入 ITCM。
- DMA 缓冲区放入 DMA 可访问且属性明确的 SRAM。
- 修改内存段时必须同步检查 MPU 和链接脚本。

### 13.3 SDMMC

- SDMMC DMA 与 FatFs 缓冲区必须正确执行缓存清理和失效。
- 写卡延迟通过环形缓冲区和低优先级 SD 任务隔离。
- 不允许在 DataRouter 或传感器高优先级任务中直接执行 `f_write()` 或 `f_sync()`。

---

## 14. SD 卡黑匣子

黑匣子是实时系统旁路记录系统，不是简单的同步文件写入。

数据路径：

```text
DataRouterTask
    ↓ 统一日志帧
bsp_ringbuffer
    ↓
SDCard_Task
    ↓
FatFs / SDMMC
```

要求：

- DataRouter 只负责生成统一帧并快速写入环形缓冲区。
- SD 任务以低优先级异步写卡。
- 所有日志使用统一帧头、消息类型、长度、序号、时间戳和校验。
- 不把 C 结构体直接裸拷贝作为永久文件协议。
- 记录入队帧、丢帧、丢字节、写入错误、同步错误、缓冲区峰值和最长写入时间。
- SD 模块封装保持简单、实用、易懂，并符合其他组件的代码风格。

## 15. 传感器协议和融合

### 15.1 MTF02

实机输出以 `$X<` 开头并包含 `0x1F01`、`0x1F02`，因此直接支持 MSPv2：

- `0x1F01`：测距消息。
- `0x1F02`：光流消息。

不强制使用上位机改成 MicoLink，驱动应直接解析当前实机协议。

### 15.2 TFmini Plus

- 支持由飞控板发送配置命令修改反馈频率。
- 接收频率和进入 ESKF 的融合频率可以分开。
- 高频接收最新测距，不代表每帧都必须执行完整协方差更新。

### 15.3 GPS

当前硬件没有 GPS：

- ESKF 不依赖 GPS 才能启动。
- GPS 接口可以保留，但默认不得把无效 GPS 数据参与融合。
- 当前主要融合 IMU、测距、光流和气压高度。

### 15.4 方差分析

传感器数据需要采集并进行方差分析，用于：

- 判断静态噪声。
- 估计量测协方差。
- 检查零偏漂移。
- 识别异常值和振动影响。
- 为 ESKF 的过程噪声和量测噪声提供依据。

统计应使用稳定、数值安全的在线算法，例如 Welford 算法，并明确采样频率、单位、静态条件和样本数量。

## 16. ESKF 和姿态任务

- ESKF 预测、观测、状态注入和发布职责分段清晰。
- 15×15 协方差传播应利用系统矩阵稀疏结构，避免没有必要的完整矩阵乘法。
- 矩阵工作区放入静态内存或 DTCM，避免高频任务栈上分配大数组。
- 热点函数可放入 ITCM，但必须通过链接映射和实机测试确认。
- 不允许为了速度删除数值检查、协方差对称化和正定性保护。
- 不同传感器的接收频率和融合频率必须区分。
- 多个观测同时到达时需要监测单轮最坏耗时。
- 姿态任务必须统计丢失 IMU 通知、无效 `dt` 和数值失败次数。

---

## 17. 初始化顺序

系统初始化必须集中管理，按照依赖顺序执行。

推荐顺序：

```text
时钟、MPU、Cache、GPIO、DMA
    ↓
UART、SPI、I2C、定时器、SDMMC、USB
    ↓
BSP实例
    ↓
SensorHub
    ↓
BMI088、BMI270、SPL06、TFmini、MTF02
    ↓
消息中心、通信、SD卡、指令
    ↓
姿态与ESKF
    ↓
可选控制和电机输出
    ↓
冻结消息拓扑并进入正常运行
```

要求：

- 所有启动结果写入统一状态结构。
- 任一必需模块失败时输出明确诊断。
- 电机输出默认关闭，只有显式安全开关打开且所有依赖成功后才能创建控制任务。
- 会使用 `FromISR()` 的模块应在调度器启动后初始化。

## 18. 错误处理和可观测性

每个硬件模块至少保留：

- 初始化状态。
- 中断次数。
- DMA 启动和完成次数。
- 总线忙丢弃次数。
- DMA 和总线错误次数。
- 数据解析错误次数。
- 最近错误码。

关键系统保留：

- HardFault、MemManage、BusFault、UsageFault 信息。
- FreeRTOS 栈溢出 Hook。
- FreeRTOS malloc 失败 Hook。
- 任务栈高水位。
- 当前和历史最小堆空间。
- 关键函数和中断最大耗时。

禁止静默吞掉错误。允许降级运行时，必须记录降级原因。

---

## 19. 编译、格式化和测试

以下规则作为强制要求：

1. 使用项目 `.clang-format` 统一格式。
2. 编译警告必须检查，新代码不得增加未解释警告。
3. 完整工程必须成功链接。
4. 协议和数学回归测试必须通过。
5. 代码质量检查必须通过。
6. 修改中断、DMA、缓存或链接脚本后必须实机验证。

当前自动测试：

```text
sensor_protocol_regression
eskf_math_regression
code_quality_check
```

文件行数不是强制门槛，`clang-format + 编译警告 + 回归测试 + 实机验证` 才是强制规则。

## 20. 实机验收标准

### 20.1 初始化

- 所有必需模块初始化成功。
- 无 HardFault、BusFault、MemManage 或 UsageFault。
- 电机安全开关状态符合预期。

### 20.2 IMU

- 至少采集 30,000 个稳态 DRDY 周期。
- 测试窗口内不得停核，避免调试器污染最大值。
- 检查周期最小值、最大值、平均值和超差次数。
- DMA 完成数应与有效 DRDY 数一致。
- DMA 启动错误和传输错误应为 0。
- 姿态任务丢失通知应为 0。

### 20.3 ESKF

- 统计平均、最大、P99 和 P99.9 单轮耗时。
- 单轮最大耗时必须低于 IMU 周期，并保留足够控制余量。
- 数值失败次数应为 0。
- 检查预测、各观测更新和发布阶段的独立耗时。

### 20.4 SD卡

- 挂载、创建文件、写入和同步正常。
- 无丢帧、写入错误和同步错误。
- 检查环形缓冲区峰值和最长 `f_write()`、`f_sync()` 时间。
- 最终需要进行 100 Hz、500 Hz 和 1 kHz 日志压力测试。

### 20.5 资源

- 记录每个任务的栈高水位。
- 记录当前和历史最小空闲堆。
- 检查 CPU 总负载和关键任务负载。
- Debug 和 Release 构建分别建立基线，不混用性能结论。

## 21. 代码评审检查表

提交或交付前逐项确认：

- [ ] 是否在独立工程副本中修改？
- [ ] 是否保持模块单一职责？
- [ ] 公共结构体和类型是否放在 `.h`？
- [ ] 是否删除了不必要的垂直换行？
- [ ] 中文注释是否解释设计原因、单位和线程上下文？
- [ ] 是否重复实现了 `user_math` 已有功能？
- [ ] BSP、Modules、Application 依赖方向是否正确？
- [ ] ISR 是否保持短小？
- [ ] 优先级 0～4 的 ISR 是否完全没有调用 FreeRTOS API？
- [ ] DMA 缓冲区是否满足 MPU/D-Cache 一致性要求？
- [ ] 函数超过 80 行是否有合理理由？
- [ ] 圈复杂度超过 15 是否已经检查？
- [ ] 是否执行了 clang-format？
- [ ] 是否通过完整编译和全部回归测试？
- [ ] 是否完成必要的实机传感器、故障和性能验证？

## 22. 总结

本工程不追求“代码越短越好”，而追求：

```text
职责清晰
接口稳定
排版连贯
注释准确
单位明确
并发安全
实时可测
错误可查
修改可验证
```

任何重构都应优先提高人的理解效率，同时保持嵌入式实时系统的确定性和安全性。
