# STM32H743 飞控实机运行性能报告

## 1. 结论摘要

本报告基于当前 `cmake-build-debug` 固件、STM32H743 实机和 J-Link/GDB 连续采样得到。测试期间电机输出编译期开关保持关闭，所有必需模块初始化成功，未出现 HardFault、MemManage、BusFault 或 UsageFault。

主要结论如下：

- 实际 CPU 主频为 240 MHz，Cortex-M7 内核版本为 r1p1。
- 1 秒统计窗口内，任务上下文总负载稳定在 36.6%～37.1%。
- 姿态 ESKF 任务是绝对主要负载，占 34.4%～35.0% CPU。
- 改进测量扰动后，ESKF 整轮平均耗时 338.62 μs，最大 763.40 μs。
- BMI088 驱动回调时间戳到姿态任务取得样本的平均延迟为 51.41 μs，稳态最大 85 μs。
- 早期报告中的 415 μs 唤醒长尾由性能任务暂停调度器扫描全部任务栈造成，不属于原业务链路。
- 连续 240,360 次姿态预测中，`missed_imu_count` 为 0，`numerical_failures` 为 0。
- 已测关键中断的累计驻留时间约占 CPU 的 1.30%；单次中断处理通常低于 6.4 μs。
- FreeRTOS 当前堆使用 8,960 B，历史峰值使用 11,120 B；最差时仍有 4,240 B 余量。
- 所有任务的历史最小剩余栈均大于其分配空间的 70%，当前没有栈紧张迹象。
- D-Cache 已启用。8 KiB 顺序读取时，热缓存比冷缓存快 1.21 倍，比 D2 非缓存 SRAM 快约 3.00 倍。
- SD 黑匣子无丢帧、无写入/同步错误；但本次业务数据只有约 1 帧/秒，属于轻负载验证，不能代替高吞吐压力测试。

## 3. CPU 与任务实时性能

### 3.1 任务 CPU 占用

三轮独立 1 秒窗口的任务上下文总负载分别为 36.9%、37.1% 和 36.6%，波动只有 0.5 个百分点。

| 任务 | 优先级 | CPU 占用 | 说明 |
|---|---:|---:|---|
| `Attitude` | 53 | 34.4%～35.0% | 1 kHz ESKF，主要计算负载 |
| `data_router` | 2 | 1.0%～1.2% | MAVLink 路由、USB 与日志生产 |
| `sensor_hub` | 52 | 0.6% | UART/I2C 传感器事件处理 |
| `sd_card` | 1 | 0.2% | FatFS 写入与周期同步 |
| `performance` | 1 | 小于 0.1% | 每秒读取一次任务快照 |
| `usb_tx` | 2 | 小于 0.1% | 当前 USB 发送流量很低 |
| `mav_rx` | 3 | 近似 0 | 测试期间没有有效上行流量 |
| `uav_cmd` | 2 | 近似 0 | 任务大部分时间阻塞等待 |
| `Tmr Svc` | 2 | 近似 0 | 软件定时器负载很低 |

FreeRTOS 运行时间统计会把一部分中断时间记到被中断的任务或 Idle 上，因此任务表不能单独给出纯 ISR 负载。关键 ISR 已用独立 DWT 探针统计，详见下一节。

### 3.2 姿态任务单轮耗时与时限

| 指标 | 实测值 |
|---|---:|
| 运行频率 | 约 1,000 Hz |
| 平均单轮耗时 | 338.62 μs |
| 最大单轮耗时 | 763.40 μs |
| 平均周期占用 | 33.86% |
| 最大观测周期占用 | 76.34% |
| 最大观测剩余时间 | 236.60 μs |
| 预测次数 | 240,360 |
| 丢失 IMU 通知 | 0 |
| ESKF 数值失败 | 0 |

分段 DWT 测量如下：

| 执行阶段 | 平均耗时 | 最大耗时 | 主要工作 |
|---|---:|---:|---|
| ESKF 预测 | 203.62 μs | 248.00 μs | 名义状态积分、两次 15×15 协方差矩阵乘法和过程噪声 |
| 全部观测处理 | 124.33 μs | 549.83 μs | TFmini、MTF02、气压计和可选磁力计更新 |
| TFmini 单次更新 | 102.30 μs | 145.47 μs | 一维测距残差、NIS、增益、状态注入和协方差更新 |
| 状态获取与发布 | 10.61 μs | 48.25 μs | 状态复制、欧拉角计算、消息发布和控制反馈 |

TFmini 串口实际约以 1 kHz 产生新帧，37,048 次预测期间完成了 37,030 次 TFmini 融合。因此几乎每轮预测都增加约 102 μs 的完整协方差观测更新，这是平均耗时较高的最主要原因之一。将 TFmini 保持 1 kHz 采样、但只按 50～100 Hz 进入 ESKF，可预计节省约 9%～10% CPU，同时避免把相邻高度噪声错误地当成完全独立观测。

多个观测源在同一个 IMU 周期到达时，会连续进行多次协方差更新，因此观测阶段最大达到约 550 μs。最大整轮耗时仍低于 1 ms，但增加磁力计、GPS 或控制计算前仍应保留时限监测。

ESKF 在该窗口内接受 265,615 组观测，拒绝 5,392 组，拒绝率约 1.99%。这是卡方门限的异常观测剔除，不是数值计算失败。

### 3.3 IMU 到任务的唤醒延迟

当前探针从 BMI088 驱动回调记录的 DRDY 时间戳开始，到姿态任务复制出一致样本结束：

| 指标 | 实测值 |
|---|---:|
| 平均延迟 | 51.41 μs |
| 最小延迟 | 50.00 μs |
| 稳态最大延迟 | 85.00 μs |
| 稳态样本数 | 36,007 |

SPI2 内核时钟约 120 MHz，当前 32 分频后总线只有约 3.75 MHz。陀螺仪 7 字节和加速度计 13 字节两段级联 DMA 的纯线上时间约为：

`(7 + 13) × 8 / 3.75 MHz ≈ 42.67 μs`

再加上两次 DMA/HAL 回调、切换片选、PendSV 和样本解析，得到约 51 μs 的稳定基线是合理的。该值主要是 SPI 传输时间，不是 FreeRTOS 调度器无故等待 50 μs。

早期记录的 415 μs 最大值来自旧版性能任务每秒调用 `uxTaskGetSystemState()`：该 API 暂停调度器并扫描所有任务的栈填充值，性能任务单次约占 0.4 ms。中断虽然仍能到达，但姿态任务暂时不能切入，因而产生人为长尾。新版只在启动阶段枚举一次任务，后续每秒扫描一个栈且允许姿态任务抢占；性能任务单次耗时降至约 73 μs，稳态唤醒最大值降到 85 μs。

该指标覆盖 DMA 链路完成和高优先级任务唤醒，但不包含传感器引脚电平变化到 C 语言 EXTI 回调记录时间戳之前的几微秒。若要测物理引脚边沿到 ISR 第一条指令的严格延迟，需要用定时器输入捕获或示波器配合 ISR GPIO 翻转。

## 4. 中断性能

下表中的时间从进入对应 C 中断函数开始，到 HAL IRQ 处理结束。低优先级中断若被更高优先级中断抢占，DWT 记录会包含被抢占时间，因此最大值反映真实的中断驻留上界。

| 中断路径 | 约频率 | 平均耗时 | 最大耗时 | NVIC 优先级 |
|---|---:|---:|---:|---:|
| SPL06 EXTI0 | 31.5 Hz | 4.92 μs | 33.30 μs | 7 |
| BMI270 EXTI9_5 | 787 Hz | 4.56 μs | 6.38 μs | 5 |
| BMI088 EXTI15_10 | 1,798 Hz | 2.53 μs | 5.88 μs | 5 |
| SPI2 RX DMA | 4,000 Hz | 0.82 μs | 2.36 μs | 5 |
| SPI3 RX DMA | 1,575 Hz | 0.90 μs | 2.46 μs | 5 |
| I2C2 RX DMA | 31.5 Hz | 2.10 μs | 17.57 μs | 7 |
| SDMMC1 | 2.1 Hz | 3.48 μs | 4.55 μs | 5 |
| USB OTG FS | 测试期仅 1 次 | 4.30 μs | 4.30 μs | 配置值 |

上述关键 ISR 的累计时间约为 CPU 的 1.30%。该值不包含 SysTick、PendSV、所有 UART DMA 和未插桩的 TX DMA，因此是已测关键中断的占用，不是全芯片所有异常的绝对总和。

中断优先级与 FreeRTOS 的 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5` 一致：调用 `FromISR` API 的 BMI/DMA 中断均处于允许范围内。TIM2 优先级为 0，但它只在 32 位微秒计数器约 71.6 分钟溢出时运行一次，且不调用 FreeRTOS API。

当前所有任务栈都很宽裕。不要仅凭 240 秒静态台架数据立刻大幅缩栈；应至少覆盖 USB 大包、MAVLink 上行、SD 卡长延迟、传感器异常和完整飞行状态后再决定。

## 6. D-Cache、MPU 与 DMA 一致性

Cortex-M7 DWT 不提供可直接读取的 D-Cache hit/miss 硬件计数器，因此不能严谨地声称“命中率为多少”。本次采用同一段 8 KiB 顺序读取的冷缓存、热缓存和非缓存 SRAM 周期对照：

| 内存场景 | 周期数 | 时间 | 近似吞吐 |
|---|---:|---:|---:|
| D1 AXI SRAM，冷缓存 | 7,434 | 30.98 μs | 264 MB/s |
| D1 AXI SRAM，热缓存 | 6,154 | 25.64 μs | 319 MB/s |
| D2 SRAM，非缓存 | 18,442 | 76.84 μs | 107 MB/s |

热缓存相对冷缓存加速约 1.21 倍，相对非缓存 D2 加速约 3.00 倍。该结果包含 Debug 构建循环和访存指令开销，只用于同固件内的相对比较。

MPU 配置检查：

- Flash：可执行、可缓存、可缓冲。
- D1 AXI SRAM 512 KiB：可缓存、可缓冲，适合算法状态和普通任务数据。
- D2 SRAM 前 256 KiB及后 32 KiB：不可缓存、可共享，覆盖完整 288 KiB。
- D3 SRAM 64 KiB：不可缓存、可共享。
- `.dma_buffer` 和 RTT/SystemView 缓冲区放在 D2 非缓存区。
- SDMMC 专用缓冲区位于 D1，磁盘驱动在传输边界执行 D-Cache clean/invalidate。

当前传感器 DMA 计数与完成计数一致、无 DMA 错误，说明现有 MPU 和 DMA 一致性方案在本次运行中正常。

DTCM 128 KiB 和链接脚本中的 `.fast_stack` 当前未使用。若将来 CPU 余量不足，可评估把 ESKF 热状态或高优先级任务栈放入 DTCM；DMA 缓冲区不能放入 DTCM。

## 7. SD 黑匣子实测

240 秒长窗口内：

| 指标 | 结果 |
|---|---:|
| 状态 | RUNNING / FR_OK |
| 入队帧 | 241 |
| 丢帧/丢字节 | 0 / 0 |
| 写入错误/同步错误 | 0 / 0 |
| 环形缓冲区峰值 | 43 B / 128 KiB |
| 最大 `f_write` 耗时 | 4.33 ms |
| 最大 `f_sync` 耗时 | 24.98 ms |
| SD 任务 CPU | 约 0.2% |

低优先级写卡任务和 128 KiB 环形缓冲区确实把最长 25 ms 的同步延迟隔离在实时链路之外。

但是当前只记录 DataRouter 发出的 MAVLink TX 帧，实测约 1 帧/秒、43 B/帧。这只能证明挂载、DMA、缓存一致性、文件写入和掉电窗口同步逻辑正常，不能证明黑匣子在 IMU/姿态高频记录下仍不丢帧。后续需要增加 100 Hz、500 Hz 和 1 kHz 的合成日志压力测试。

`SD_CARD_SYNC_PERIOD_MS` 当前为 500 ms，即使没有新数据也会约每秒执行两次 `f_sync()`。在当前轻负载下影响很小，但高频记录时建议改成“有新写入且到达同步周期才同步”，减少无效命令和卡写放大。

## 9. 风险排序与下一步

### P1：降低 TFmini 进入 ESKF 的融合频率

当前 TFmini 以约 1 kHz 执行完整 ESKF 更新，单次平均消耗约 102 μs。建议继续以高频接收最新测距，但增加测量时间门控，以 50～100 Hz 融合，并按照实际融合周期设置量测噪声。预计可将姿态任务平均 CPU 从约 34.6% 降至约 25%。

### P1：给 ESKF 留出更明确的最差时限余量

当前最大单轮 763.40 μs，多个观测同周期到达是主要长尾。加入更多融合源或控制计算前，应继续保留探针，并在真实飞行振动、完整遥测和高频日志同时开启时复测。

### P1：补做 SD 高吞吐压力测试

当前 1 帧/秒远低于黑匣子预期负载。建议按统一帧格式生成可配置速率的测试流，至少覆盖 100 Hz、500 Hz、1 kHz，并验证环形缓冲区峰值、丢帧数、写卡长尾和文件 CRC。

### P2：启用 FreeRTOS 内存故障 Hook

已有 Hook 代码但配置未开启。建议启用二级栈溢出检查和 malloc 失败 Hook，并在故障快照中记录任务名、SP、剩余堆及 CFSR。

### P2：保留 Debug 与 Release 两套基线

本报告是 `-Og`。应再烧录 `RelWithDebInfo` 或 Release，在同样硬件负载下复测 CPU、ESKF 最大耗时和 ISR 长尾，形成可比较的性能回归基线。

### P3：确认 FreeRTOS Cortex-M7 portable 选择

当前构建实际使用 `portable/GCC/ARM_CM4F/port.c`，而芯片是 Cortex-M7 r1p1。现有固件能够稳定运行，但建议固定到项目已验证的 Cortex-M7 port 版本，避免未来升级 FreeRTOS 或编译器后由自动回退改变上下文切换实现。

## 10. 本次加入的可重复测量设施

新增 `App_Performance` 模块提供：

- `performance_snapshot`：GDB/Ozone 可直接查看的稳定快照。
- FreeRTOS 任务运行时间、CPU 千分比和栈高水位。
- 当前/历史 FreeRTOS 堆使用量。
- 关键 EXTI、SPI/I2C DMA、SDMMC 和 USB 中断耗时。
- ESKF 单轮工作耗时。
- BMI088 回调到姿态任务取样延迟。
- 冷缓存、热缓存、非缓存 SRAM 对照测试。

测量任务每秒运行一次，CPU 占用低于 0.1%，且全部使用静态内存。它不参与控制决策，也不改变电机安全开关。
